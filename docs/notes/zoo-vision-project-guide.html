1. What Zoo Vision is

Zoo Vision is AI video analytics for one park, Taman Safari. About 12 cameras watch cashier desks, the restaurant (occupancy and tables), the vehicle gate and the pony rides. A Python vision engine runs YOLO detection and ByteTrack tracking on each camera. It turns what it sees into events (a vehicle crossed the gate), intervals (a desk was unattended from 10:02 to 10:09) and metrics (restaurant occupancy each minute). A NestJS API stores them in Postgres and serves them to a web dashboard, along with live video, snapshots and clips.

Ground rules of the design

  • One park, one on-site server. No cloud, no multi-site, no tenants. Everything runs in one Docker Compose stack on a GPU server at the park.
  • The database is the source of truth for config. An admin adds cameras and draws zones in the web UI. A change applies live, between two frames, with no stream drop and no restart of other cameras.
  • Use cases will change and grow. Adding one must not need a database migration. Each use case is defined once, as JSON Schemas in packages/contracts, and the TypeScript and Python types are generated from them.
  • Nx Witness is optional. It was the centre of the prototype. Now MediaMTX records the video and Nx is kept only as a possible future integration (integrations/nx/plugin/, frozen).
  • Small team. One backend/CV developer owns this repo; a frontend team builds the dashboard against a versioned contract.

2. The system at a glance

Eight services in one Compose stack, plus the browser. The engine and the API never import each other's code. At runtime they talk through Redis, and the engine also fetches its camera list from the API over HTTP.

The four paths through the system

PathRoute
AnalyticsCamera → MediaMTX → engine → Redis stream events → API ingest → Postgres → REST and WebSocket → dashboard
ConfigDashboard → API saves a new config version → Redis cfg:changed → engine fetches from /internal/engine/cameras → worker applies it between two frames → status shows the applied version
Live videoBrowser → Caddy /media/webrtc (after forward_auth to GET /api/v1/auth/check) → MediaMTX WHEP. Boxes come separately: engine → Redis cam:{id}:boxes → API → WebSocket room camera:{id} → canvas over the video
EvidenceEngine writes the event snapshot to /data/snapshots; MediaMTX records continuously; the API's pin job copies a clip window from MediaMTX playback into /data/evidence for events worth keeping

3. The parts, one by one

Engine: services/engine/ (Python 3.12, uv)

One process holds a supervisor and one worker thread per camera. Each worker owns its stream (core/stream_manager.py) and its use case pipeline. The supervisor (core/supervisor.py) keeps the set of workers in line with the cameras the API says this engine should run.

  • Config comes from the API, not files. At start, and on every cfg:changed message, Redis reconnect, or 60 s timer, the engine calls GET /internal/engine/cameras?group=<ENGINE_GROUP>. Its only static config is environment variables (REDIS_URL, ENGINE_TOKEN, API_URL, DEVICE, …).
  • Use cases are plug-ins. Each is a folder usecases/<id>/pipeline.py holding one BasePipeline subclass. They are found by scanning the folder, so adding one doesn't mean editing a central list.
  • Shared model pool (core/model_pool.py): one loaded model per (file, image size), shared by every camera that uses it, with an inference thread that can batch frames (ENGINE_MAX_BATCH).
  • Outputs: stream messages through core/event_stream.py (built by core/messages.py), a status heartbeat every 5 s (core/status.py), a JPEG frame every 2 s, per-frame boxes, and event snapshots (core/snapshot_store.py).
  • Model jobs: the engine also validates uploaded models and converts .pt to ONNX, taking jobs from the Redis list model:jobs (core/model_jobs.py).
  • Engine groups: each camera has an engineGroup. A second engine process with another ENGINE_GROUP can take some cameras, for example a crash-prone one.

API: apps/api/ (NestJS 11, Prisma 7)

Everything the browser and the engine need from the backend. Each folder in src/ is a Nest module:

Contracts: packages/contracts/ (JSON Schema)

The single source of truth for the stream messages, the per-use-case settings and live values, and the WebSocket messages. npm run generate writes TypeScript types (for the API and one self-contained file for the frontend) and Pydantic models (into services/engine/contracts/). CI fails if the generated files are out of date, so the engine, API and dashboard can't drift apart.

Supporting services

MediaMTX

Pulls each camera once and records it. It re-serves the stream over RTSP to the engine, over WebRTC to browsers, and serves clip playback on :9996. The API adds and changes its paths at runtime through the Control API (:9997), so adding a camera in the UI needs no SSH.

Redis

The only channel between API and engine, plus session storage. AOF persistence means the event stream survives a Redis restart.

Postgres

Config, users, logs and the three analytics tables. The running API connects as zoo_api, which can't update or delete analytics rows; migrations run as the owner role zoo_owner.

Caddy

One origin for everything: / to the dashboard; /api, /ws and /media to the API; /media/webrtc to MediaMTX after an auth check; /internal/* answers 404. One origin means plain cookies and no CORS.

Gotenberg

Headless Chromium that turns the dashboard's print-styled report page into a PDF summary.

web (separate repo)

zoo-vision-fe, Next.js + Tailwind. UI only: it talks to the API from the browser and never touches the database.

4. How data moves

4.1 From a camera frame to a row in Postgres

1 DetectThe worker runs the model and tracker, then the use case rules (zones, tripwire, timers).
→
2 SnapshotFor an event, it draws boxes and zones on the frame and saves a JPEG to /data/snapshots.
→
3 XADDIt appends a contract-checked message to the Redis stream events. Once that returns, the event is durable.
→
4 IngestThe API reads batches as consumer group api, writes them in one transaction (idempotent on message id), then ACKs.
→
5 PushAfter the commit: event.created and data.changed over the WebSocket.

There are four message kinds: event, interval_open, interval_close (the two share a session id) and metric. Delivery is at-least-once with no double counting: if the API crashes mid-batch, it re-reads its unacknowledged entries on restart and the inserts are idempotent.

If this fails……this happens
API or Postgres downMessages wait in the Redis stream and are processed when it comes back. The engine carries on.
Redis briefly downThe engine holds events in a small bounded memory buffer and reports how many it dropped (events_dropped).
A bad messageInvalid, or failed too many times: it goes to the DeadEvent table and is ACKed, so it never blocks the rest.
Engine restartIt sends engine_started; the API closes that group's open intervals with endReason = engine_restart.
Camera goes darkIts status key expires after about 15 s; the API opens a camera_offline interval, so reports can tell "no rides" from "camera off".

4.2 A config change reaching a running camera

1 EditA manager draws zones on the camera's latest frame (GET /cameras/:id/frame).
→
2 SavePOST /cameras/:id/config with baseVersion. The API checks the schema and role rules and stores version N+1.
→
3 NotifyThe API publishes cfg:changed {cameraId, version} on Redis.
→
4 ApplyThe engine fetches its cameras, validates the settings with Pydantic and the worker applies them between two frames.
→
5 ConfirmStatus reports appliedVersion = N+1, or a configError while it keeps running N.
  • Every event carries the configVersion it was produced under, so a jump in a report can be traced to an edit.
  • Rollback makes an older version active again by creating a new version; history is never rewritten.
  • Two people editing at once: the second save gets 409 STALE_VERSION.
  • What a change costs: geometry and thresholds apply on the next frame and keep tracks and counts. Tracker tuning restarts track ids once. A new model loads in the background and then swaps in. A new source URL reconnects only that camera. A new use case rebuilds that camera's pipeline.

4.3 Live view and evidence

  • Video: WebRTC (WHEP) straight from MediaMTX, H.264 passed through without re-encoding. Caddy lets the call through only after GET /api/v1/auth/check answers 204.
  • Boxes: the browser joins the WebSocket room camera:{id}. The API subscribes to Redis cam:{id}:boxes only while someone is in that room, and the browser draws the boxes on a canvas over the video.
  • Use case overlays (table badges, occupancy, desk state) are drawn by the dashboard from the camera's status, so the engine never encodes live video.
  • Debug view (superadmin only): /media/debug/:id shows the engine's own annotated frames as MJPEG. The engine draws them only while someone is watching.
  • Clips: GET /media/clips/:eventId serves a kept clip from /data/evidence, or cuts the window around the event from MediaMTX's recordings while they still exist. Clips are kept automatically for warning and critical events and every event on an audit camera, and by hand with POST /events/:id/evidence.

5. Data model

Postgres via Prisma (apps/api/prisma/schema.prisma). Times are stored in UTC; reports use the site time zone (Asia/Jakarta by default, a site setting).

Analytics: stored by shape, not by use case

Every use case produces some mix of three shapes, so three generic tables hold all of them. A new use case adds rows, not tables; its specific fields live in a data JSONB column checked against its contract.

TableShapeKey columnsExamples
EventSomething happened at a momenttime, camera, useCase, type, severity, configVersion, schemaVersion, snapshot path, datavehicle crossing, pony departure, capacity alert
IntervalA state that lastedcamera, useCase, kind, subjectId, start, end, endReason, datatable session, desk unattended, camera offline
MetricA number over time, one row per minutecamera, useCase, name, minute, valueoccupancy, queue length

The pattern mirrors OpenTelemetry's logs, spans and metrics. Live state (current occupancy, fps) is never stored here; it lives in Redis cam:{id}:status.

Config, people and logs

A summary; every column, key and index is in section 6.

Append-only by design. The API's database role can only SELECT and INSERT on Event, AuditLog, LoginLog and DeadEvent, and can update only specific columns of Interval and Metric. Counts can't be quietly edited, which the future fraud module relies on. Every migration that adds a table must also add its GRANTs (see apps/api/README.md).

Do I need a migration?

Usually not. A new field on a use case's events, intervals, metrics or settings is a contract change (npm run generate in packages/contracts), not a migration. A Prisma migration is for the structural tables, new tables and new indexes.

Every camera use case also has the model settings (model_id, imgsz, confidence_threshold) and an optional nx_bookmark. Settings marked x-minRole: SUPERADMIN in the schema (model, tracker tuning) can only be changed by a superadmin; the API checks this on save.

Adding or changing a use case

  1. Write the contract: packages/contracts/usecases/<id>/ with its schemas and examples, then npm run generate and npm test.
  2. Write the engine pipeline: services/engine/usecases/<id>/pipeline.py, one BasePipeline subclass, plus tests under tests/.
  3. No migration and no dashboard change are needed for it to appear in the generic event, interval and metric views. A custom report page in the dashboard is optional.
Change rules. Only add optional fields. Never rename, remove or change the meaning of a field. A breaking change bumps the use case's schemaVersion; old rows keep theirs and stay readable.

8. Users, roles and login

Three fixed roles, SUPERADMIN > MANAGER > USER. A superadmin is normally a Magnet engineer, a manager is the customer's admin and a user is a viewer. Hiding menu items in the UI is only a convenience; the API decides.

ActionUSERMANAGERSUPERADMIN
Dashboards, live view, events, camera status and frames, CSV and PDF exports, reading site settingsyesyesyes
Zones, thresholds, enable or disable a camera, config history and rollbackyesyes
Users (except superadmins), models list, system log, keeping an event's clipyesyes
Stream URLs, model, tracker tuning, engineGroup, use case, audit flag, recording settingsyes
Create or delete cameras, superadmin accounts, API tokens, model upload and jobs, editing site settings, debug viewyes

How login works

  • POST /api/v1/auth/login sets a zoo_session cookie (HttpOnly, SameSite=Lax). The session lives in Redis and slides 12 hours from the last request, ending 7 days after login at the latest. Disabling a user or changing a role takes effect on their next request.
  • Scripts, Postman and Swagger can use an API token instead: Authorization: Bearer <token>. Tokens are created by a superadmin, stored hashed, carry a role and can be revoked. The WebSocket accepts only the cookie.
  • Protection: logins are limited to 10 a minute per address, and five wrong passwords in 15 minutes lock the account (423 ACCOUNT_LOCKED). Every attempt goes to the login history.
  • The engine is a third kind of caller: it sends ENGINE_TOKEN, and only to /internal/engine/*.
Errors have one shape everywhere: {statusCode, code, message, errors?}. Switch on code (stable) rather than message. The full list, with what the UI should do for each, is in docs/fe-contract.md section 4; the codes are defined in apps/api/src/common/errors.ts.

Rules the frontend must follow

  • REST is the truth; the socket only nudges. There is no replay: after every connect or reconnect, refetch what the page shows and subscribe to rooms again. Build tables from REST, not from event.created.
  • Only call the API from the browser. The session is a cookie in the browser; the Next.js server has none.
  • Open the app through Caddy in development (http://localhost:8080), not the Next.js port, or cookies and the socket won't work.
  • 401 → login page. 403 → show the message (and for ROLE_REQUIRED, disable the fields it names). A session.ended message means the same as a 401, except role_changed: refetch /auth/me and reconnect.
  • Switch on code, not message, for every error.

How the frontend stays in sync with the backend

The backend publishes a contract: three files at a git tag contract-vX.Y on the backend repo. In the frontend, npm run contract:pull <tag> fetches them and runs orval, which generates a typed axios client from the OpenAPI file.

FileGives the frontend
apps/api/openapi.jsonEvery REST endpoint with its parameters and response types → the generated hooks (useCamerasList, …)
packages/contracts/generated/web/index.d.tsTypes for every socket message (ServerToClientEvents, ClientToServerEvents) and each use case's settings, events, intervals and live values
docs/fe-contract.mdHow it behaves: roles, error codes, paging, report parameters, media, socket rooms, and a changelog per tag

Until v1.0, a breaking change is allowed only with a changelog entry. From v1.0, changes to /api/v1 are additive only.

11. WebSocket and engine channels

WebSocket for the browser: socket.io at /ws

WebSocket transport only, session cookie only, and the Origin must match the host. The message types are in packages/contracts/ws/ and in the frontend's generated types file.

MessageRoomWhen
event.createdalerts (everyone)Each new event, after the ingest commit
data.changedalertsAt most every 5 s after commits: tells pages to refetch their data
status.snapshotstatus (on request)Every 2 s while anyone is in the room: all cameras' live status
boxescamera:{id}Up to 10 a second while anyone is in the room: {t, sentAt, boxes}, coordinates 0 to 1, track ids
audit.noticemanagersSomeone changed an audit camera
disk.warningmanagersA data disk crossed 85% (warning) or 95% (critical), once per crossing
session.endeduser:{id}The session was ended (logout elsewhere, disabled, role change); then disconnect
subscribe / unsubscribesent by the clientJoin or leave status or a camera:{id} room

Redis: the contract between engine and API

Key or channelDirectionPurpose
stream eventsengine → APIDurable events, interval open and close, metric samples
pub/sub cfg:changedAPI → engine"Camera X has a new config version"; the engine then refetches its cameras
hash cam:{id}:status (TTL ~15 s)engine → APIHeartbeat every 5 s: fps, state, applied version, error, live counters. If it expires, the camera is offline
key cam:{id}:frameengine → APILatest raw JPEG every 2 s, for the zone editor and grid thumbnails
pub/sub cam:{id}:boxes, key cam:{id}:activeboth waysPer-frame boxes for the live overlay. The API keeps the active key alive while a browser is in the camera's room; only then does the engine publish boxes
key cam:{id}:debug, pub/sub cam:{id}:debugframesboth waysWhile the API keeps the key alive, the engine publishes annotated JPEGs for the debug view
list model:jobsAPI → engineModel validation and conversion jobs

The live values each pipeline puts in its status are typed per use case by packages/contracts/usecases/<id>/live.schema.json. The engine test tests/test_live_contract.py catches a renamed field before the dashboard does.

How the frontend uses these messages, and the contract files it builds against, are in section 9.

14. Glossary

TermMeaning
Use caseA kind of analysis a camera runs (cashier presence, vehicle gate, …). Defined by its contract; implemented by one engine pipeline
PipelineThe engine class for one use case: takes detections and tracks, applies zones and timers, produces messages and live values
ContractThe JSON Schemas in packages/contracts that every part generates its types from
Config versionOne saved set of a camera's settings. Versions only increase; rollback makes a new one
Event / Interval / MetricThe three shapes of analytics data: a moment, a span of time, a number per minute
EnvelopeThe common wrapper of every stream message (kind, camera, time, config version, schema version, data)
Engine groupThe set of cameras one engine process runs (ENGINE_GROUP)
Zone, ROI, tripwirePolygons and lines drawn on the camera image, in 0 to 1 coordinates. A tripwire counts crossings; an ROI limits where detection counts
Audit cameraA camera whose config changes are flagged and notified and whose evidence is kept longer, because moving a tripwire is the easiest way to hide sales
Evidence / kept clipAn event's video clip copied out of the continuous recording so it outlives the normal retention
Dead eventA stream message that could not be stored, parked in DeadEvent so it doesn't block the rest
WHEPThe WebRTC playback protocol MediaMTX uses for live video in the browser
ANPRAutomatic number plate recognition, used at the vehicle gate (ADR-005)
ByteTrackThe multi-object tracker that gives each detection a stable id across frames (ADR-007)
x-minRoleA schema annotation on a settings field: the lowest role allowed to change it
